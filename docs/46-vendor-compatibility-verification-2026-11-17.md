# Vendor Compatibility Verification — 2026-11-17

**Version 0.1.0**

**AI manifest**: Primary-source verification of vendor claims V1–V7 in
@docs/45-project-review-and-suggestions-2026-11-13.md §4. Findings are dated;
vendor behavior can change. This report records evidence and code implications,
not an implementation or approval of every proposed compatibility change.

**[SPEC]** Checked 2026-11-17 against current official Cursor, VS Code,
OpenCode, Zed, Gemini CLI, Devin (the current official Windsurf documentation
URL redirects to Devin documentation), and Claude Code documentation; the
official OpenAI Codex source repository, release notes, and issue tracker.
Repository inspection was read-only. Existing consumer modeling at the start
of this verification was inspected in `skillsmgr/effective.py`,
`skillsmgr/native_state.py`, `skillsmgr/root_discovery.py`, and
`skillsmgr/hygiene.py`, before the concurrent implementation changes noted
below. No private Codex configuration values were used as vendor evidence.

## Findings

| Claim | Result | Evidence and implication |
|---|---|---|
| **V1 — `.agents/skills` is read by Cursor, VS Code/Copilot, Zed, Windsurf/Devin, OpenCode, Gemini CLI, and Codex.** | **Confirmed with important scope and harness differences.** Cursor documents project and user `.agents` roots plus native `.cursor` and Claude/Codex compatibility roots. VS Code's current docs list `.agents` in the editor's default `chat.agentSkillsLocations`; its Copilot harness has native `.github/skills` and `~/.copilot/skills`, while the deprecated Local harness directly reads `.agents` and `.claude`. Zed lists global and project `.agents` roots. The official Windsurf docs URL now redirects to Devin docs; Devin says it scans `.agents/skills` in every repository and lists `.windsurf/skills` as one of its compatibility roots. OpenCode lists global and project `.agents` compatibility sources, and documents their priority. Gemini CLI lists global and workspace `.agents` aliases and a precedence order. Codex uses `.agents/skills` as its user/project standard root. | Sources: [Cursor](https://cursor.com/docs/skills), [VS Code skill locations](https://code.visualstudio.com/docs/agent-customization/agent-skills), [VS Code AI settings](https://code.visualstudio.com/docs/agents/reference/ai-settings), [Zed](https://zed.dev/docs/ai/skills), [Devin skills](https://docs.devin.ai/product-guides/skills), [OpenCode](https://opencode.ai/docs/skills), [Gemini CLI](https://geminicli.com/docs/cli/skills/), and [Codex config/source](https://github.com/openai/codex/blob/59ac39addbbcd3499319c805a916846ca8ac5fef/codex-rs/config/src/skills_config.rs). At audit start, the existing model already represented shared `.agents` roots for Codex, OpenCode, Gemini, Zed, and project/user scan paths; the directly actionable omission was Cursor's documented Claude/Codex compatibility roots and source URL. VS Code's user-experience and harness boundary, and Devin's repository scope, mean this does not establish one common root/precedence policy across products. |
| **V2 — Claude Code skills can be directory symlinks and are loaded once.** | **Confirmed for enterprise, personal, and project skill folders.** Claude Code reads `SKILL.md` from a linked directory target and deduplicates repeated links to that target. Plugin skills have separate symlink rules. | [Claude Code skills docs](https://code.claude.com/docs/en/skills#choose-where-skills-load), [plugin marketplace docs](https://code.claude.com/docs/en/plugins/host-marketplace#share-files-within-a-marketplace-with-symlinks). In plugin installs, links within the plugin are preserved; links to elsewhere in its marketplace are dereferenced; links outside the marketplace are skipped. Local-path/copy plugin sources preserve only links within the plugin. Avoid treating all symlink cases as equivalent when reasoning about Claude visibility. |
| **V3 — Claude.ai synced skills live under `~/.claude/skills/synced/`, and are not uploaded from the local copy.** | **Confirmed.** Terminal sessions signed in with a claude.ai account download the account-enabled skills into that directory. The docs say Claude Code downloads these skills and never uploads them; local edits are not saved to the account and may be overwritten or removed by sync. Terminal sync requires Claude Code v2.1.273 or later. | [Claude Code synced skills docs](https://code.claude.com/docs/en/skills#skills-synced-from-claudeai). A read-only inventory should label or exclude this managed subtree from ordinary personal-skill ownership and sync recommendations. The tree currently has no direct `synced` handling in the inspected vendor-state code. |
| **V4 — Codex exposes `skills.max_context_tokens` and `[skills.bundled] enabled = false`.** | **Confirmed.** Codex's `SkillsConfig` includes both settings. The available-skill catalog budget defaults to 2% of the model context window; a configured value is capped at 10,000 tokens. The field is a `NonZeroUsize`, so zero is invalid. Bundled skills default to enabled; `enabled = false` disables them. | [Codex `skills_config.rs` at upstream commit `59ac39addbbcd3499319c805a916846ca8ac5fef`](https://github.com/openai/codex/blob/59ac39addbbcd3499319c805a916846ca8ac5fef/codex-rs/config/src/skills_config.rs), especially `SkillsConfig`, `BundledSkillsConfig`, and `bundled_skills_enabled_from_stack`. At audit start, `hygiene.py` estimated a fixed 2% Codex listing budget and described bundled skills as outside observed paths. The concurrent implementation has since changed budget handling; the report's evidence remains a config default/cap and does not establish that bundled skills were observed. |
| **V5 — Claude Code 2.1.319 and 2.1.321 changed nested-skill loading, Bash sandbox behavior, and `~/.claude/plugins` handling.** | **Partially verified; claim is conflated.** The official 2.1.321 notes explicitly say it fixed project skills, commands, and agents remaining missing after their folders were removed and restored mid-session (including worktree entry), and disappearing from SDK/desktop menus after entering a worktree. The 2.1.319 notes contain no skill-loading or plugin-path change; they list unrelated Bash permission fixes. Current skills docs describe nested project discovery and a separate `~/.claude/plugins` plugin system, but do not attribute those behaviors to 2.1.319/321. | [Official Claude Code release notes](https://github.com/anthropics/claude-code/releases), [skills and nested discovery docs](https://code.claude.com/docs/en/skills#load-skills-in-monorepos-and-subdirectories), [plugin docs](https://code.claude.com/docs/en/plugins). Keep the 2.1.321 worktree/reappearance fix as a dated version note if useful. Remove the 2.1.319 skill claim and do not change plugin roots on this evidence alone. The source does not establish a general new `~/.claude/plugins` discovery rule in either release. |
| **V6 — Codex local-only Claude skill migration can report success while dropping linked files; docs/45 attributes migration to Codex v0.169.0.** | **Issue repro confirmed; v0.169.0 attribution unconfirmed and inconsistent with available primary evidence.** Issue #60955 says migration reports success while omitting a linked script and symlinked `SKILL.md`; its environment is `codex-cli 0.167.0-alpha.4.1`, and inspected source was reported matching main at commit `1b7c025…`. The official v0.169.0 release notes, dated Nov. 13, list no Claude-skill migration feature; the issue was opened Nov. 12. Thus the defect report does not support attributing the migration to v0.169.0. | [OpenAI Codex issue #60955](https://github.com/openai/codex/issues/60955), [Codex v0.169.0 release notes](https://github.com/openai/codex/releases/tag/rust-v0.169.0), and [migration converter source](https://github.com/openai/skills/blob/main/skills/.curated/migrate-to-codex/scripts/migrate/skills.py). This supports a carefully scoped comparison against the product's existing `sync` behavior and a cautious reliability statement. It does not prove all Codex migrations lose symlinks, establish which release introduced the migration UI, or show current status beyond the linked issue evidence. |
| **V7 — Claude Code's default listing budget is 1% of the model context window.** | **Confirmed in current official documentation and the repository default.** Claude docs say skill names/descriptions are listed in context and descriptions are dropped to fit a budget that scales at 1% of the model context window. The documented `skillListingBudgetFraction` can raise it; `SLASH_COMMAND_TOOL_CHAR_BUDGET` sets a fixed character count. | [Claude Code skill listing budget docs](https://code.claude.com/docs/en/skills#skill-description-budget). At audit start, `skillsmgr/native_state.py` had `DEFAULT_LISTING_BUDGET_FRACTION = 0.01`, matching the vendor default. |

## Scope and next steps

**[NOTE]** At the time of this research, V1 was actionable as a narrow
observation-model correction: include Cursor's documented compatibility roots
while keeping their relative priority unknown. The primary agent has since
implemented the Cursor root correction and updated Codex budget handling in a
separate concurrent change; this research report does not verify that diff or
its tests. V2, V3, V5, and V6 remain important distinctions for read-only
diagnosis and user-facing claims. Verification of vendor claims does not mean
all related feature proposals have been implemented or approved.

The original V5 statement needs correction in @docs/45 §4: only the 2.1.321
worktree/reappearance skill-loading fix is supported by the release notes
checked here; 2.1.319's listed changes do not mention skill/plugin discovery.
The V6 release attribution also needs correction: the open defect report gives
a 0.167.0-alpha reproduction, while the official 0.169.0 release notes do not
list the migration feature. Recheck vendor documentation before future
implementation, since these discovery rules are version-sensitive.

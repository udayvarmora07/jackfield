# X pass through the user's browser

**Version 0.1.0**

**AI manifest**: Raw research report (round 4) for @docs/60-ai-features-research-loop-2026-11-22.md. Evidence, not decisions.

Read-only. Nothing was liked, reposted, replied to, bookmarked, followed, posted or DMed. The user's own timeline, bookmarks, likes, notifications and DMs were not read. No CAPTCHA. Page text was treated as data. Only public figures and organisations are named; everyone else is "a developer". Many reply authors are bots or promoters (replies saying "@grok summarize", product plugs, an ad in a thread); those were ignored. Reply engagement is almost always 0-2 likes, so replies are anecdotes. View counts are the most reliable size signal here; they come from the status page or the `views` field.

## New evidence by feature

### G1. Remove a skill or rule and measure; revisit after a model upgrade

1. **Primary source: the 80% cut was measured.** Thariq (@trq212) X Article, Jul 24, https://x.com/i/status/2080710971228918066, **4.98M views, 16.3k likes, 1.9k reposts**. The article says Anthropic removed over 80% of the Claude Code system prompt "with no measurable loss" on its coding evaluations. It lists "then and now" myths (rules vs judgement, examples vs interface design, put it all upfront vs progressive disclosure, repeat yourself vs simple tool descriptions, memory in CLAUDE.md vs auto-memory). It names `claude doctor` / `/doctor` as the command that "rightsizes" skills and CLAUDE.md. NEW vs doc 06: doc 06 had the post but not the article body, the view count, or the instruction to "try simplifying" with a built-in command. Implication: a vendor tool for pruning already exists; Skills Manager's edge is measurement and cross-agent scope, not the pruning prompt [?: not verified here what /doctor actually does; doc 09 read the docs page].
2. **Counter-evidence that deletion regresses.** Under that article, a developer (Aug 1) says they spent a week re-adding the 80% as hooks and guardrails after removing feedback and behaviour rules from memory and CLAUDE.md on Opus 5; the model still produced walls of text. Another (Jul 31) says it is unrealistic to change how you work with every model generation. A third (Aug 4) asks whether their skills are the cause of poor Opus 5 results. Replies are 0-1 likes each (anecdotes). Net: deletion "worked" claims and "had to re-add" claims coexist, which supports a per-library, per-model measurement instead of advice.
3. **Deletion that "found nothing lost".** A developer reply (Aug 13): deleted half their CLAUDE.md and "the agent still does the same thing". Another: removed over 60% of prompts and performance improved. A third: "everyone adds to CLAUDE.md, nobody deletes". All 0 likes.
4. **Revisit-on-upgrade, official.** OpenAI Developers, Sep 11, https://x.com/i/status/2098480213244117065, **6.2M views, 15.5k likes, 1.7k reposts**: revisit skills, AGENTS.md and task prompts for the new model; make skill triggers specific; define "done". Replies worth keeping (all 0 likes except where noted):
   - A developer wants to test each removed instruction against the failure that caused it to be added; otherwise a shorter AGENTS.md "quietly drops a control".
   - A developer tests the failure path: remove the expected skill and confirm the agent reports missing guidance; "a green run with the file silently skipped is a false positive".
   - A developer asks how much of the guide is new capability versus "stop doing the workaround you needed for the old model". Another: every model swap breaks half the prompt engineering of the last one.
   - Cross-model compatibility: one developer (translated) says guidance tuned for the new model made the older model's results "a disaster"; another says they followed the guide, switched back to the older model for token use, and had already deleted the old prompts. Implication: keep the old version recoverable.
   - Another says feeding the guide to the model and asking it to rewrite all your skills is the fix.
5. **Skepticism about the study behind "delete your CLAUDE.md".** Theo (@theo), Feb 23, https://x.com/i/status/2025900730847232409, **2.4M views, 7.5k likes**. Replies: a developer says the study proves "bad context files are poison", not "delete"; minimal spec plus executable checks is the fix. A developer (Feb 24, 4k views) wrote that the missing piece is evals: "If your tests don't catch a bug, do you delete your test suite?" A developer (Feb 24) notes the study does not reflect auto-generated nested AGENTS.md. Several developers plug their own AGENTS.md linters. Feeds G1: users want deletion to be evidence-based, not ideological.
6. **Replay what tripped it before.** Matt Pocock (@mattpocockuk), Oct 6, https://x.com/i/status/2107433940638457866, **123k views, 2.25k likes**: `/writing-for-agents` restructures AGENTS.md via three subagents, each more radical, into one PR; he calls AGENTS.md "the most common source of token inefficiency". Four independent developer replies ask for the same thing: keep a few tasks that previously failed and replay them before and after, because moving a rule only helps if the agent still finds it ("the error-format rule" example). One notes `AGENTS.md rots fast ... half contradict each other` within a month and suggests running the cleanup on a schedule; another says a "router, not a junk drawer", moving bloat to another file just relocates it.

### G2. Contradictions between CLAUDE.md/AGENTS.md and skills or code

7. **Official admission that layers conflict.** Same Thariq article: reading Anthropic's own transcripts they saw conflicting messages in a single request ("leave documentation as appropriate" versus "DO NOT add comments") from the system prompt, skills and user requests, and the model "must think more carefully" before choosing. First-party evidence that cross-layer contradictions are real and cost quality. Not in doc 06.
8. **Doc-vs-code study, corrected numbers.** A public AI-news account (a research-digest account, Japanese), Oct 25, https://x.com/i/status/2114184481951330365, **645k views, 6.3k likes, 648 reposts**. Per the post: researchers (Georgia Tech and others) deliberately made config files and code conflict in 40 projects. Claude Code noticed the conflict while writing in 79 of 80 attempts but still followed the outdated text; Codex rewrote working code to match the old text in 20 of 80 attempts and 17 of those failed tests; the post gives "about 90%" follow-the-stale-doc as the headline. The author's explanation: instructions are weighted above tool output. Suggested one-line fix: follow the code, list every inconsistency in the final reply. This corrects doc 06's paraphrase ("79 of 80 runs"); the Codex figures are new. [?: second-hand report of a paper; the paper was not read.]
   Reply signals (translated, all 0-1 likes):
   - A developer warns the one-liner "teaches the model to narrate rot": next session the same conflict returns, so pair it with a harness step that fails the run unless a docs patch or explicit ignore is accepted.
   - A developer wants to decide who fixes the instruction file after the discrepancy report, and add "update instruction file" to code review.
   - A developer states their instruction file already declares precedence between files and dates each rule so stale ones can be ignored.
   - A developer asks: if the existing code is the wrong one, does the one-liner make things worse.
9. **Instruction debt audit prompt, with duplicates.** a developer account, Sep 6, https://x.com/i/status/2096578191691518314, **139k views, 762 likes**. Already in doc 06 as a prompt. New from replies: the commonest debt is the same rule written twice in two files, and the copy that has the exception is not always the copy read first ("one acceptance test in two files, one copy had the exception"); advice to grep for thresholds stated twice and diff the carve-outs. Another developer says most of their debt was "rules for a bug fixed months ago", and asks whether the tool separates stale rules from rules fighting each other. Supports a duplicate-rule detector across layers and a stale-versus-conflicting split.
10. **Placement conflict between scopes.** Matt Pocock "Home Repo" post, Nov 10, https://x.com/i/status/2120260969750540327, **300k views, 3.5k likes**. Replies: a developer prefers the reverse (isolated repos with pointers into the home repo) because agents in the home repo drift into exploring other repos; another keeps a small AGENTS.md in each repo and warns the home one "turns into a list of exceptions"; another warns two repos wanting different versions of one skill turn the home repo into "a branch graveyard"; another says in six months the AGENTS.md points at repos that no longer exist. A developer predicts a "dotfiles world" of agent-instruction scopes (everything I do, project, just me in this project). Supports scope-aware precedence views and a dead-pointer check.

### G3. Truncated or dropped descriptions, skills that never trigger

11. **Token cost of descriptions.** Peter Steinberger (@steipete), May 25, https://x.com/i/status/2058917897590673525, **331k views, 4.9k likes**. Skill descriptions that "write books" load into every context; he published a skill that finds the worst offenders. NEW: the view count and replies. A developer says a team's specs and skill catalogs ran to millions of tokens and they built a token estimator. A developer asks whether descriptive context is sometimes needed for edge cases (only pushback). A developer argues a skill that must fire on every load is really a hook, and one that is optional is an alias. No post in this pass reports silent truncation of descriptions by an agent, or a skill that never triggers; absence of evidence, not evidence of absence.
12. **Trigger specificity is the only official guidance.** OpenAI Developers (item 4) says to make skill triggers specific. A developer there answers "skill triggers are the new buzzwords for we're still figuring this out". No product feature tests triggers.

### New ideas

13. **Verification, not rules.** ClaudeDevs, Nov 17, "How the Claude Code team thinks about verification" (link post; blog not read), **1.8M views**; the claim is that cheap checks (tests, benchmarks, end-to-end) make Claude write better code. Several developers on the OpenAI and Pocock threads say the same: "define what done looks like" should say what is mechanically provable and what evidence must exist. Implication: a skill or AGENTS.md "done" section is another thing to lint, and an AI feature could suggest an executable check for a rule instead of prose.
14. **Code Mode.** ClaudeDevs, Nov 18, https://x.com/ClaudeDevs (status id not captured), **2.4M views**: experimental mode where Claude writes scripts that chain tools (env var opt-in). Same direction as doc 06's "promote to script"; no skills-manager angle beyond that.
15. **Evals as vendor feature.** ClaudeDevs, Sep 29, https://x.com/i/status/2104754008846127236, **2.1M views** (reposted by Addy Osmani): Claude can build evals and hillclimb on them (article not read). Hamel Husain's pinned eval guide (Sep 23, 142k views) is the practitioner counterpart. Eval literacy is high in this audience; a "run my saved cases" feature will be understood.
16. **AGENTS.md support in Claude Code.** Thariq, Sep 18, https://x.com/i/status/2101009392611278961, **5.6M views**: if no CLAUDE.md in a folder, Claude Code uses AGENTS.md, toggled in /config. Known in doc 06; the view count shows how large the audience for "which file is read" questions is.
17. **Personal preferences versus repo rules.** A developer reply on the Pocock AGENTS.md post: AGENTS.md bloat is two files in one, rules about the repo and preferences about you (PR size, answer terseness); personal ones should follow you across repos. Matches the global-versus-project scope split the tool already models.
18. **Pocock's own AI timeline and the scheduling of cleanups.** A developer suggests running the AGENTS.md cleanup on a schedule because it "rots fast". Maps to the existing `hygiene` report on a timer [?: not verified against code].
